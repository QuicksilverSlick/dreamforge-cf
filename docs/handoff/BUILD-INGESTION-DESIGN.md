# Build Ingestion Design — any-file attachments + web research in the build pipeline (researched 2026-07-11)

Upstream verdict: NOTHING to port (image-only attachments; web_search chat-only upstream too). Build fork-side on our existing spines: image-attachment multimodal path, referenceSite Browser-Rendering ingestion, core.ts tool loop (depth 7, already coexists with structured output).

## Design summary

Both features are built fork-side by extending three pipelines the fork already owns — the image-attachment multimodal spine (upload -> R2 uploads/ -> ProcessedImageAttachment -> createMultiModalUserMessage into templateSelector/blueprint/chat/phase ops), the reference-site Browser Rendering ingestion (worker/services/referenceSite/ingest.ts: probe + screenshot + 12k-char text profile injected into the blueprint prompt), and the existing recursive tool-execution loop in worker/agents/inferutils/core.ts (depth 7, works WITH structured-output schemas but is only consumed by the chat processor today). Upstream cloudflare/vibesdk has nothing to port for either ask (verified: image-only attachments identical to ours; web_search chat-only there too). FEATURE 1 (any-file attachments): a generalized Attachment type (discriminated kind: image | document | text | data) uploaded via a new authenticated multipart endpoint streamed to R2 (not base64-in-JSON — 128MB isolate), with extension + magic-byte + MIME allowlist validation server-side. Extraction happens at upload time, Cloudflare-native: env.AI.toMarkdown() (binding already live, wrangler.jsonc "ai" remote:true) converts pdf/docx/xlsx/xls/ods/odt/csv/numbers/html/xml to markdown for free; txt/md/json/yaml/code pass through with UTF-8 decode + truncation; images keep the existing multimodal image_url path untouched; pptx/.doc/audio/video rejected in v1. Direct-to-model file parts are a verified dead end on our AI Gateway /compat path (only text + image_url parts exist in inferutils/common.ts), so extract-to-markdown-first is the architecture. Context injection is summarize-then-inject PLUS chunked retrieval: original + full extracted markdown live in R2 as sibling objects; a cheap summarization pass produces a ~2k-token structured summary per doc; blueprint gets summaries + a bounded excerpt budget (~50k chars total across all attachments, alongside formatReferenceSite/formatInterviewSpec); a new read_attachment tool lets the agent pull specific char-ranges/chunks of the full text on demand during chat and build — no vector infra needed. FEATURE 2 (build-time web research): two mechanisms sharing one new service. worker/services/web/pageIngest.ts = fetch + env.AI.toMarkdown(html, {cssSelector}) for static pages with Browser Rendering (/markdown quick action on the existing env.BROWSER binding) as the JS-heavy fallback, all gated by the existing urlSafety.ts SSRF/robots guards and hard caps; it replaces the naive 4000-char regex-strip in web-search.ts (DRY). Then (a) a deterministic pre-blueprint research step ingests user-cited URLs into BlueprintGenerationArgs exactly like reference-site text, and (b) tools [web_search, read_webpage, read_attachment] are passed into executeInference for blueprint and PhaseGeneration only (PhaseImplementation excluded in v1 — its SCOF streaming re-streams on tool-loop recursion). Security: mirror upstream #387 — a sanitizeUntrustedText util (strip CommonMark link-reference definitions, delimited untrusted-content blocks) wraps ALL extracted doc text and fetched web text before prompt interpolation. Sparks metering rides the existing per-inference metering with new agentActionNames (attachmentSummary, buildResearch) plus a per-op tool-call budget.

## Upload pipeline (feature 1)

CLIENT: generalize src/hooks/use-image-upload.ts into use-attachment-upload.ts; chat input + home page get an any-file picker. Files are uploaded FIRST via the new endpoint and only attachment ids/keys ride the /chat/new URL and POST /api/agent body (fixes the current base64-images-in-URL-params pattern in src/routes/home.tsx:86 and restores the dropped client-side size check). -> API: new authenticated + rate-limited POST /api/attachments (multipart/form-data, streamed; new worker/api/controllers/attachments/controller.ts + route). Server-side validation: allowlist by extension AND magic-byte sniff AND declared MIME (all three must agree); caps 25MB/file (images stay 10MB), ~8 files/build; no content execution ever — bytes go straight to R2. -> STORAGE: R2 TEMPLATES_BUCKET uploads/<id>/<filename> (original) + uploads/<id>/extracted.md (extraction output), reusing the uploadImageToR2 key/metadata pattern in worker/utils/images.ts:144-150; DO state holds only { r2Key, extractedKey, summary, kind } references, never blobs (matches the existing base64-strip discipline). -> EXTRACTION (at upload time, in-worker, safe: parses only, never executes): FILE-TYPE MATRIX — [pdf, docx, xlsx, xlsm, xls, ods, odt, csv, numbers, html, xml] -> env.AI.toMarkdown() (free, ~4MB proven envelope per file — Cloudflare AI Search's own limit on the same converter); [txt, md, json, yaml, toml, source code] -> UTF-8 decode + truncate, no conversion; [png, jpeg, webp] -> UNCHANGED existing multimodal image path (base64 -> image_url parts, blueprint 'high' detail); [pptx, legacy .doc, audio, video, archives, executables] -> rejected in v1 with a clear message (pptx = jszip fast-follow). -> SUMMARIZATION: docs whose extracted text exceeds the excerpt budget get one cheap-model pass (agentActionName 'attachmentSummary', Sparks-metered) producing a structured summary; full markdown stays in R2. -> CONTEXT INJECTION: blueprint user message gains a formatAttachedDocuments section (sibling of formatReferenceSite at worker/agents/planning/blueprint.ts:182-242 and formatInterviewSpec) containing per-doc summary + excerpt under a global ~50k-char attachment budget, each wrapped in sanitized untrusted-content delimiters; ProcessedAttachment[] threads through BlueprintGenerationArgs from agent controller.ts:243-257; phase ops (PhaseGeneration/PhaseImplementation userContext) get summaries + the read_attachment chunked-retrieval tool for on-demand deep reads; mid-build WS attachments extend the pendingUserImages flow in behaviors/base.ts (persisted to DO state, fixing the current in-memory-only eviction bug at base.ts:204). Data files (csv/json) additionally bindable as app seed assets via a fileAssets manifest (generalizing blueprint.imageAssets) in a later PR.

## Web ingestion (feature 2)

SEARCH: the existing SerpAPI web_search tool (worker/agents/tools/toolkit/web-search.ts, env.SERPAPI_KEY, graceful no-key fallback) is already generic — the gap is purely that only UserConversationProcessor passes tools into executeInference (customTools.ts:42 registers it in chat buildTools only; blueprint.ts:348, PhaseGeneration.ts:254 pass none). The core tool loop (core.ts:824-907, MAX_TOOL_CALLING_DEPTH=7) already coexists with structured-output schemas, so enabling build-time search = passing a build-scoped tool list [web_search, read_webpage, read_attachment] into blueprint and PhaseGeneration executeInference calls, with a per-operation tool-call budget (e.g. 5 searches + 5 page fetches per op) and activity-chip narration reusing the #235 plumbing. PhaseImplementation is explicitly EXCLUDED in v1: its SCOF stream feeds a file parser and tool-loop recursion re-streams — wiring tools there needs dedicated work. PAGE INGESTION: new shared worker/services/web/pageIngest.ts with a two-tier strategy — tier 1: plain fetch + env.AI.toMarkdown(html, { cssSelector }) (free, static pages); tier 2 fallback for JS-heavy pages: Browser Rendering /markdown quick action on the existing env.BROWSER binding (the same binding referenceSite/ingest.ts:246 uses via puppeteer; Workers Paid includes 10 browser-hrs/mo). Every fetch is gated by worker/services/referenceSite/urlSafety.ts (validateReferenceUrl SSRF guard + robots.txt) — critical because the current fetchWebContent (web-search.ts:171-196) has NO SSRF protection and a naive regex HTML-strip capped at 4000 chars; it gets refactored onto pageIngest (raising the cap to ~20k chars/page, N-page budget per build), which upgrades chat-side URL ingestion for free (DRY). DETERMINISTIC PRE-BLUEPRINT RESEARCH: URLs the user cites in their prompt/interview get ingested before blueprint generation as background work (same pattern as the interview controller's reference-site kickoff at interview/controller.ts:87-116) and injected into BlueprintGenerationArgs as a formatWebResearch section. INJECTION POSTURE: all fetched page text passes through the #387-style sanitizeUntrustedText util inside delimited blocks before any prompt interpolation. Deep-reuse note: full reference-site ingestion (palette/logo/asset harvest) stays a separate, richer path — pageIngest is text-context only.

## Risks

- env.AI.toMarkdown scale behavior is unverified beyond the documented format list: the ~4MB envelope is inferred from Cloudflare AI Search's limit on the same converter; huge PDFs, scanned/image-only PDFs (no OCR), and pathological spreadsheets need an early spike in PR 2 before committing the format matrix to users.
- Prompt injection via uploaded documents and fetched web pages is now a first-class attack surface (upstream shipped #387 for exactly this): the sanitizer + delimited untrusted blocks are mandatory in PR 2/4, and residual risk remains — an attacker-authored PDF can still steer generation content.
- Privacy of uploaded documents: the existing /api/uploads/* route serves R2 uploads PUBLICLY (fine for images feeding previews, wrong for a financials.xlsx); PR 1 must decide access control before shipping, not after.
- PhaseImplementation tool-loop hazard: the SCOF stream feeds a file parser and the inference tool loop re-streams on recursion — enabling tools there without rework corrupts file parsing; the design excludes it, but future contributors may 'just add tools' there (guard with a comment/test).
- Context-window blowout: attachments now stack on top of reference-site profile (12k), interview spec, and images in the SAME blueprint message — budgets must be global across all context sources, not per-feature, or long-interview + multi-doc builds will overflow smaller design-role models.
- Cost/runaway loops: SerpAPI quota and Browser Rendering hours under build-loop usage; depth-7 recursion cap is not a cost cap — the per-op tool budget and Sparks attribution in PR 5 are load-bearing, and the operator-exemption user must not skew cost telemetry.
- pendingUserImages is already lossy (plain class field, dies on DO eviction) — PR 3 builds on this flow, so the persistence fix is a correctness prerequisite, not a nice-to-have.
- New unauthenticated-surface / abuse risk: the multipart endpoint must sit behind auth + the existing rate-limit infra with per-user storage quotas; anonymous-build attachment abuse mirrors the anon-build concern already flagged for the save-deploy funnel work.
- R2 storage creep: uploads/ has zero cleanup today; adding 25MB documents accelerates it — lifecycle policy (PR 6) should not slip more than one cycle.
- Gemini/compat constraints may shift: /compat is deprecated in favor of the ai/v1 endpoint and Anthropic is now a /compat provider — the extract-first architecture is robust to this, but revisit direct file parts only if the inference path migrates off OpenAI-shaped messages.

### Platform research for any-file-type ingestion + build-time web research on Cloudflare Workers (verified July 2026). Bott

- RECOMMENDED EXTRACTION ARCHITECTURE: env.AI.toMarkdown() — binding already present (wrangler.jsonc:58-61 "ai":{"binding":"AI","remote":true}). Verified supported formats (docs, July 2026): PDF, DOCX, XLSX/XLSM/XLSB/XLS/.et, ODS/ODT, CSV, Apple Numbers, HTML, XML, images (jpeg/png/webp/svg/gif/bmp — AI-captioned via Workers AI object-detection + image-to-text models). NOT supported: PPTX, legacy .doc, plain text/markdown (pass-through, no conversion needed). New since Mar 2026: conversionOptions (html.cssSelector, image.descriptionLanguage, pdf metadata exclusion); .supported() endpoint (Oct 2025) lets us gate client-side by exact mime list at runtime.
- toMarkdown COST/LIMITS: free for all non-image conversions; image captioning bills Workers AI neurons (10,000 free/day, then $0.011/1k neurons — Workers Paid). No documented per-file cap, but Cloudflare's own AI Search uses the same converter with a 4MB/file limit — treat ~4MB as the proven envelope, and keep our images on the existing vision path (toMarkdown captioning is redundant with multimodal models).
- DIRECT-TO-MODEL FILES ARE A DEAD END on our gateway path: inference builds OpenAI-shaped messages with only `text` + `image_url` parts (worker/agents/inferutils/common.ts:12-20, createMultiModalUserMessage:76-102) routed via AI Gateway /compat or provider-override endpoints incl. Gemini's OpenAI-compat URL (worker/agents/inferutils/core.ts:203-229, 358-370). Gemini's OpenAI-compat layer does not accept inline PDFs (images only); CF /compat docs list no file-part translation. Note: /compat is now marked deprecated in favor of api.cloudflare.com/client/v4/accounts/{id}/ai/v1/chat/completions (still works indefinitely), and Anthropic is now a supported /compat provider — relevant to the Opus-on-compat memory but a separate workstream. Verdict: extract-to-text first; only images go multimodal.
- SIZE LIMITS (verified): Workers request body 100MB Free/Pro, 200MB Business, 500MB Ent; isolate memory 128MB; R2 5GiB single PUT / 4.995TiB multipart (irrelevant at our scale). Current image path sends base64 inside the POST /api/agent JSON body (worker/api/controllers/agent/controller.ts:220-225, 10MB/image, 2 images max per worker/types/image-attachment.ts:70-75).

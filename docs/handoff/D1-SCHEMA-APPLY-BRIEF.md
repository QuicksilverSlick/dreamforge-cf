# D1 Schema-Apply Best-Practices Brief (researched 2026-07-09)

Doc-backed design for platform-side `applyInitialSchema` on per-app D1 databases.
Sources: Cloudflare D1 docs + wrangler source (main), remote-bindings docs, better-auth 1.6 docs/source, upstream vibesdk audit. Companion to docs/handoff/SANDBOX-TO-PROD-CONTINUITY.md.

## Best-practices brief

As of July 2026 there is NO first-class Cloudflare tooling for applying schema to dynamically-created per-tenant D1 databases — the canonical, doc-backed pattern is exactly what we planned: the platform (the only party holding a real API token) applies migrations out-of-band, immediately after database creation, via POST /client/v4/accounts/{acct}/d1/database/{uuid}/query. This is byte-for-byte the mechanism `wrangler d1 migrations apply --remote` uses internally: wrangler sends each migration as ONE multi-statement /query call containing the migration file's full text plus an appended `INSERT INTO d1_migrations (name) values ('<filename>.sql');`, after priming the bookkeeping table with `CREATE TABLE IF NOT EXISTS "d1_migrations"(id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT UNIQUE, applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL);`. Cloudflare's own signals all converge on this shape: (1) the official d1-template applies migrations as a separate step BEFORE dev (`dev: seedLocalD1 && wrangler dev`) and BEFORE deploy (`predeploy: wrangler d1 migrations apply DB --remote`) — the vite plugin has no migration hook and never auto-applies schema, local or remote; (2) the "Enterprise AI vibe coding platform" reference architecture blesses unique-D1-per-application but ships no provisioning/migration tooling — schema is explicitly the platform's job; (3) D1 docs call the REST API "best suited for administrative use," which one-shot schema provisioning is; (4) no dynamic bind-by-uuid exists (bindings are deploy-time-static; workers-sdk #8563 open; Worker Loader only re-exposes statically-bound resources), so binding.exec() is impossible platform-side and REST /query is the only option. Endpoint choice: /query (documented to support "multiple statements, joined by semicolons, executed as a batch"), NOT /import (presigned-R2 + polling flow for bulk files up to 5 GB, with a DB-unavailable window) and NOT /raw (same as /query, just array-shaped results). better-auth confirms the pattern from its side: for drizzle users it explicitly delegates schema application to external tooling (`npx auth generate` → `drizzle-kit generate` → apply yourself; `auth migrate`/getMigrations are Kysely-only, and getMigrations calls process.exit(1) on other adapters), performs zero DDL and zero DB introspection at runtime, and only needs the four core tables (user/session/account/verification — unchanged in the 1.7 RC) to exist. Remote-bindings D1 dev traffic rides the edge-preview Cap'n Web session, not the REST API — consistent with our authorizing proxy's deny-by-default design; the container never needs (and can never use) a real token for schema. Critical hard-won caveats: multi-statement /query has no explicitly documented rollback-on-failure guarantee at the REST layer (D1 is auto-commit; partial application is empirically proven in workers-sdk #6348), so idempotent DDL + retry-until-verified is mandatory; BEGIN TRANSACTION/COMMIT must never appear in the SQL; the platform token strictly requires D1:Edit since the 2025-05-02 permissions fix; and /query shares the global 1,200-requests/5-minutes account API rate limit with every other platform call. Upstream vibesdk is no help: its ResourceProvisioner has the identical create-empty-D1-never-migrate bug, and upstream's "fix" was abandoning per-app D1 for DO SQLite — no cherry-pick will ever land.

## Fix validation: validated-with-refinements

- Mirror wrangler's exact call sequence, not a bespoke one: (1) prime `CREATE TABLE IF NOT EXISTS "d1_migrations"(id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT UNIQUE, applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL);` (2) idempotency gate `SELECT name FROM d1_migrations;` and skip if already seeded, (3) one /query whose sql = full 0001_init.sql text + appended `INSERT OR IGNORE INTO d1_migrations (name) values ('0001_init.sql');` — INSERT OR IGNORE (vs wrangler's plain INSERT) plus the UNIQUE(name) column makes retries safe.
- The seeded bookkeeping name must be EXACTLY the bare filename relative to migrations_dir — '0001_init.sql', no 'migrations/' prefix, exact casing — because wrangler's unapplied-check is pure name-string comparison (no checksums); any mismatch silently defeats dedup and a later apply re-runs the schema against live data. Keep the template's wrangler.jsonc on default migrations_table/migrations_dir so the seed stays valid.
- Do NOT rely on batch atomicity: the REST doc never promises rollback-on-failure and partial application is proven (workers-sdk #6348). Every statement in 0001_init.sql must be idempotent (CREATE TABLE IF NOT EXISTS / CREATE INDEX IF NOT EXISTS / INSERT OR IGNORE), and applyInitialSchema must end with a verification query (SELECT name FROM sqlite_master WHERE type='table') checking user/session/account/verification + app tables, retrying with backoff on failure.
- Send the raw multi-statement file text unsplit, exactly like wrangler's --command path (no client-side splitting); strip any BEGIN TRANSACTION/COMMIT/SAVEPOINT lines (D1 rejects them); drizzle's '--> statement-breakpoint' markers are harmless comments; keep each statement under the 100 KB limit (trivially true).
- Check BOTH the top-level success/errors[] envelope AND every result[].success per statement (plus result-array length = statement count); handle HTTP 429 with bounded backoff — the 1,200 req/5 min limit is per-user across dashboard+token combined, so an unbounded retry loop can lock out the entire platform token (D1 creates, deploys, Time Travel restores) for 5 minutes.
- Verify the platform token has D1:Edit — since the 2025-05-02 security fix, HTTP API writes strictly require it; a token that can create databases but only read D1 will fail applyInitialSchema.
- The platform must execute the SAME artifact it ships: read 0001_init.sql from the template source (the file that goes into the zip), never a hand-maintained copy in the worker — wrangler's name-only bookkeeping means content divergence is silently considered 'applied'.
- Make the apply loop iterate migrations/*.sql in sorted order rather than hardcoding 0001, seeding a bookkeeping row per file — free future-proofing for template migrations 0002+.
- Docs nuance (usage.md): the seed makes re-apply unnecessary from token-holding environments (user's laptop), but in-container `wrangler d1 migrations apply --remote` still HARD-FAILS at the authorizing proxy (even listing applied migrations is a REST /query the proxy 403s). Docs must say 'do not run --remote in the sandbox; the platform pre-applies migrations', not 'it will no-op'.
- FK safety: D1 always enforces foreign keys and PRAGMA foreign_keys cannot be toggled — order tables parent-first (user before session/account) in 0001_init.sql, or prepend `PRAGMA defer_foreign_keys = true;`.
- better-auth side: keep the drizzle schema.ts + 0001_init.sql as an inseparable generated pair (npx auth@latest generate → drizzle-kit generate); never hand-normalize the SQL (timestamp-mode mismatch corrupts dates); do NOT add DB DEFAULT clauses or autoincrement (better-auth supplies id/createdAt/updatedAt application-side); do NOT attempt getMigrations in the provisioner (Kysely-only, calls process.exit(1)); pin better-auth exactly (caret ^1.6.23 will resolve to 1.7.x when it leaves RC); keep rateLimit on default memory storage or the missing rateLimit table 500s every auth request.

## Implementation checklist (ordered)

1. Verify the platform's Cloudflare API token includes D1:Edit permission (strictly required for HTTP API writes since 2025-05-02); confirm with a test /query write against a scratch DB.
2. Template packaging: ensure migrations/0001_init.sql is included in the vite-cf-d1-runner template zip, generated as a pair with the drizzle schema.ts (`npx auth@latest generate` → `npx drizzle-kit generate`); sanity-check the DDL against the better-auth 1.6 core schema (singular camelCase user/session/account/verification; user.email UNIQUE; session.token UNIQUE; session.userId + account.userId TEXT NOT NULL REFERENCES user(id) ON DELETE CASCADE; account.password nullable; booleans as INTEGER; NO DB defaults or autoincrement).
3. Harden 0001_init.sql for non-atomic application: convert all DDL to CREATE TABLE IF NOT EXISTS / CREATE INDEX IF NOT EXISTS; ensure no BEGIN TRANSACTION/COMMIT/SAVEPOINT lines; order tables parent-first (user before session/account/verification) or prepend `PRAGMA defer_foreign_keys = true;`; optionally add the docs-recommended indexes the generator omits: session(userId), account(userId), verification(identifier).
4. Confirm the template's wrangler.jsonc uses default migration config (no migrations_table/migrations_dir/migrations_pattern overrides) so bookkeeping seeds match wrangler 4.107.0's defaults ('d1_migrations' table, './migrations' dir).
5. Implement applyInitialSchema in the platform worker's D1 provisioner (alongside the existing POST /d1/database create call), sourcing SQL from the same template artifact shipped in the zip. Sequence per migration file, iterating migrations/*.sql in sorted order: (a) POST /query with `CREATE TABLE IF NOT EXISTS "d1_migrations"(id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT UNIQUE, applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL);` (b) POST /query `SELECT name FROM d1_migrations;` and skip files already recorded; (c) POST /query with sql = full file text + `\nINSERT OR IGNORE INTO d1_migrations (name) values ('<filename>.sql');` — one multi-statement string, unsplit, exactly wrangler's remote-apply shape.
6. Response handling: treat failure as (HTTP error) OR (top-level success !== true) OR (any result[].success !== true) OR (result array shorter than statement count); surface errors[] into the provisioning failure path; bounded retry (e.g. 3 attempts, exponential backoff) with explicit 429 handling — never unbounded (shared 1,200 req/5 min token budget).
7. Verification gate: after apply, POST /query `SELECT name FROM sqlite_master WHERE type='table';` and assert user, session, account, verification + app tables exist before marking the app's D1 provisioned; fail provisioning loudly (retry or surface to user) if not.
8. Wire ordering: applyInitialSchema runs synchronously right after D1 creation and BEFORE the container env / preview session is built (extends the existing eager-provision flow from #222), so the first registration attempt in preview already has tables.
9. Update the template's usage.md: state that migrations are pre-applied by the platform; explicitly instruct never to run `wrangler d1 migrations apply --remote` inside the sandbox (it hard-fails at the authorizing proxy, it does not no-op); note that laptop-side applies with the user's own token WILL no-op thanks to the seeded d1_migrations rows; keep `--local` apply documented for local dev.
10. Pin better-auth to an exact version in the template's package.json (ship the lockfile in the zip if possible) so an unpinned container install can't drift to 1.7.x against a 1.6-generated schema; leave rateLimit on default memory storage.
11. Add a template-authoring version-bump playbook (repo docs or CI): on any better-auth bump run `npx auth@latest generate --yes` + `npx drizzle-kit generate` — empty diff proves no drift; non-empty diff becomes migrations/0002_*.sql (which the apply loop already handles).
12. Test plan: unit-test the /query payload builder (statement assembly, bookkeeping append, BEGIN/COMMIT stripping); integration-test against a real scratch D1: fresh apply → verify tables + bookkeeping row; re-run applyInitialSchema → no-op; laptop `wrangler d1 migrations apply <db> --remote` with a real token → 'no migrations to apply'; E2E: generate a D1-flagship app, register a user in preview, confirm the user row lands in the remote per-app D1.

## Risks & gotchas

- Multi-statement /query is NOT reliably atomic: D1 is auto-commit, the REST docs' 'executed as a batch' wording does not explicitly promise rollback, BEGIN/COMMIT are rejected ('cannot start a transaction within a transaction'), and partial application is empirically proven (workers-sdk #6348 — failed apply grew the DB, created no table, left no bookkeeping row). Idempotent DDL + verify + retry is the safety net, not optional.
- wrangler's applied-migration check is name-only (TEXT UNIQUE, no content hash): a seeded '0001_init' (missing .sql), a path prefix, a casing change, or a renamed file in a later template rev silently defeats dedup → wrangler re-runs the migration against live user data. Conversely, if executed SQL and shipped file content diverge, wrangler silently considers it applied. Filenames are frozen forever; one artifact is the source of truth.
- The global Cloudflare API rate limit (1,200 req/5 min) is per USER across dashboard + all tokens combined: a retry storm in applyInitialSchema can 429 D1 creates, deploys, Time Travel restores, and the owner's dashboard browsing for 5 minutes.
- D1:Edit is strictly required for HTTP API writes since 2025-05-02 — an over-permissioned-elsewhere token that only has D1:Read fails schema apply even though DB creation may succeed with account-level perms.
- In-container `wrangler d1 migrations apply --remote` still hard-fails post-fix (the applied-migrations listing is itself a REST /query the authorizing proxy 403s) — docs must route users away from it, not promise a no-op.
- better-auth never validates schema at startup: any column/table mismatch surfaces only as a runtime 'no such table/column' at first query — the platform apply is the only safety net. Do not hand-edit the generated SQL (timestamp-mode mismatches corrupt dates); do not call getMigrations anywhere in a Worker (Kysely-only, process.exit(1), uncatchable).
- ^1.6.23 will auto-resolve to better-auth 1.7.x once it leaves RC. Core tables are confirmed unchanged in 1.7, but CLI/Node requirements and plugin behavior change — pin exact.
- PRAGMA foreign_keys cannot be toggled on D1 (always enforced); only `PRAGMA defer_foreign_keys = true` works and auto-resets — table ordering in the DDL matters.
- Do not conflate wrangler's --file path with our approach: `d1 execute --remote --file` uses /import (presigned R2, polling, brief DB-unavailable window) — /import behavior docs do NOT apply to our /query plan; /query is the migrations-apply precedent.
- If rateLimit.storage is ever flipped to 'database' in a generated app's better-auth config, every auth request 500s unless a rateLimit table (id, key, count, lastRequest bigint) was migrated first — keep default memory storage.
- vite-plugin pin context (adjacent, for any future un-pin): 1.42.0+ has a silent Node >=22.18 floor via a static `registerHooks` import from node:module (no engines field, no CHANGELOG note; fails with a cryptic 'does not provide an export named registerHooks'); 1.41.x is the safe ceiling on older Node (only unsafe if experimental.newConfig is enabled); Bun's runtime lacks module.registerHooks entirely, so vite must always run under Node (default `bun run` is fine, `bun --bun` is not).
- D1 jurisdiction (eu/fedramp) can only be set in the create call, never after — if data residency ever becomes a requirement, the provisioner create body is the only place to honor it.
- No upstream convergence coming: vibesdk's ResourceProvisioner has the identical empty-D1 bug and upstream moved generated apps to DO SQLite (ctx.storage), explicitly forbidding per-app D1 — never expect a cherry-pick for this subsystem.

## Future-proofing

- vite-plugin un-pin path: 1.37.1 → 1.41.x is safe on current container Node (do NOT enable experimental.newConfig); going to 1.42.0+ (current 1.43.2) requires container Node >=22.18.0 and wrangler ^4.108.0, and vite must execute under Node (never `bun --bun` — Bun lacks module.registerHooks). Add a CI smoke test that `import('@cloudflare/vite-plugin')` succeeds under the container's exact Node before any bump, since the Node floor is unannounced in metadata.
- better-auth schema drift: 1.7 changes no core tables (all churn is plugin tables), so the current 0001_init.sql survives the 1.7 bump — but pin exact versions and run the regenerate-and-diff playbook (`npx auth@latest generate --yes` + `drizzle-kit generate`; empty diff = no drift) on every bump. Any non-empty diff becomes migrations/0002_*.sql, which the loop-over-migrations apply design already handles; never edit 0001 in place (name-only bookkeeping would mask it).
- Multi-migration future: wrangler does not reliably sort migration files (workers-sdk #13568, filesystem-order dependent) — keep zero-padded numeric prefixes and have applyInitialSchema sort explicitly; seed ALL filenames present in the zip.
- Fleet-wide schema upgrades of already-provisioned apps (CONT-next): prefer the community 'lazy migration' pattern (check schema version on first access, apply incrementally) over a mass REST sweep across thousands of tenant DBs — the 1,200 req/5 min global limit makes bulk sweeps slow and disruptive; wrangler 4.x's migrations_pattern (changelog 2026-06-04) only matters if the template ever adopts a nested ORM migration layout.
- Upstream vibesdk convergence: none coming for this subsystem — upstream removed per-app D1 from its agent vocabulary in favor of DO SQLite and its ResourceProvisioner still has the create-empty bug; treat applyInitialSchema as a permanent fork divergence and document it as such in CLAUDE.md's divergence list.
- Watch items: workers-sdk #8563 (in-Worker migration application / dynamic D1 binding) would let a future version replace REST /query with a binding-native path if it ever ships; Vite Environment API is still not-stable in Vite 8 — expect plugin churn; D1 jurisdiction-at-create (2025-11-05) is the hook if EU data residency becomes a product requirement.
- Rate-limit budgeting: as app-creation volume grows, D1 create + 3-4 /query calls per provision against the shared 1,200 req/5 min token budget caps provisioning at roughly 200-300 apps/5 min before starving other platform API traffic — if that ever binds, batch the bookkeeping-prime + apply into fewer calls and consider a dedicated service token to isolate budgets (note the limit is per-user, so a separate token under the same user does NOT add headroom — a separate account-member service user would).
